# db01 업로드 계약 재사용성 개선

현재 상태 `3290825`를 기존 db01에 fast-forward한 뒤 진행했다. 기존 브랜치 이력과 미추적 작업 파일은 보존했다. 이번 변경은 업로드/재시도의 수집 호출과 분류 결과 계약에 한정한다.

## 변경 내용

| 위치 | 이전 문제 | 변경 |
|---|---|---|
| `ingest_adapter.call_ingest` | 업로드 흐름이 수집 함수의 선택 인자와 반환 자료형을 직접 해석 | 기존/현재 수집 함수의 호출 차이, dict/dataclass 변환, 재사용 결정값 검증을 어댑터로 모음 |
| `classification.classification_fields` | 저장용 분류 검증과 UI 반환의 필드 선택이 서로 달라 실패 결과가 불완전 | 저장·반환이 네 분류 필드의 정규화 함수를 공유 |
| `upload_service.upload_result` | 분류 실패 후 업로드 성공 결과가 UI에서 INVALID_RESPONSE로 거부될 수 있음 | 실패·과거 누락 보고서도 완전한 분류 필드로 반환 |
| `jobs_repo._merge_stage_reports` | 과거 보고서를 같은 내용으로 재저장해도 추가된 기본 필드 때문에 충돌 | 분류 표현만 정규화해 비교하고 실제 성공 내용 변경은 계속 CONFLICT로 거부 |

분류 미실행은 `{}`다. 실패 또는 잘못된 값은 `auto_doc_type=''`, `doc_type_confidence=0.0`, `company_match=''`, `classify_status='failed'`다. 실패한 추정값과 원시 오류는 반환하지 않는다. 최종 유형 결정 세 필드의 검증은 기존 `decision_fields`를 사용하며 분류 기준 자체를 DB에서 다시 구현하지 않는다.

수집 호출에는 공개 메타데이터와 자동 분류 옵션을 나누어 전달한다. 재시도 분류값은 호출 전에 검증하고 사본을 전달한다. 따라서 수집기가 인자로 받은 dict를 변경해도 저장된 결정값 비교를 우회하거나 호출자 원본을 수정할 수 없다.

## 보존한 계약

1. `upload_document`·`retry_upload`의 공개 인자 및 기존 dict 반환 형식.
2. 중복 조회의 회사 범위와 현재 후보 제외, 파일 경로·해시·크기 검증.
3. 권한 재검증·회사별 DB 문맥·잠금 순서·외부 작업 중 SQL 잠금 해제.
4. 청크 소속과 최종 유형 일치 검사·활성 버전 비교·게시 및 복구 절차.
5. 기존 수집기의 선택 인자 호환과 분류 미실행 시 결과 필드 생략.

DB 스키마 및 실제 운영 문서 데이터는 변경하지 않았다. 수집·UI 운영 소스는 변경하지 않았으며 기존 UI 반환 검증기를 호출하는 회귀 검사를 추가했다. 범용 CRUD, 일괄 인자 객체, 별도 프레임워크는 도입하지 않았다.

## 검증 방법

수집 실패 결과가 DB 정규화→업로드 반환→기존 UI 검증기를 통과하는지 검사한다. 실제 격리 MySQL에서는 업로드 게시 후 작업 보고서와 반환 필드, 활성 버전 ID를 대조한다. 과거 보고서 재저장·실제 내용 변경 거부·인자 dict 변조 시 CONFLICT도 확인한다.

전체 회귀는 MySQL 8.4.13의 새 로컬 DB 6개에서 실행한다. 공개 DB URL·CA·회사 계정 설정은 시험 프로세스에서 격리하고 OpenAI·임베딩은 시험 대역을 사용한다. 실행기는 생성한 임시 서버를 종료하고 시험 폴더를 정리한다. 실제 DB·LLM 통합 성능이나 브라우저 사용성 검증을 의미하지 않는다.

최종 결과: **684개 통과, 실패·오류·건너뜀 0개, 79.785초**. 실행 로그는 Git 제외 `data/db01-refactor-final-tests.log`에 보관했다. 앞선 실행에서는 로컬 시험 DB에 공개 DB용 CA가 섞여 1건 실패했으며, 시험 프로세스의 `DB_SSL_CA`를 빈 문자열로 명시해 격리한 뒤 전체 재검증했다. 운영용 인증서 검증을 끄거나 운영 설정을 변경한 것은 아니다.
