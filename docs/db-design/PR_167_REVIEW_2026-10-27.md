## Standards

운영 코드에서 문서화된 개발 규칙 위반은 발견하지 못했다. 기존 DB_contract의 일반 함수·dict, 바인딩 SQL, 호출자 TX, 인증→DB 의존 방향을 유지한다. 한자·깨진 독스트링도 발견하지 못했다. 이전 중복 시계·컬럼 조회 제안은 현재 develop의 공통 함수 재사용으로 반영됐다.

**판단사항 1건 — 시험 DB 실행 안전성.** `hyundap/tests/test_auth_railway_ddl.py:42–43`은 고정 이름의 DB를 사전 `DROP DATABASE IF EXISTS`한다. 부모 URL이 127.0.0.1/전용 auth DB인지 확인해도 삭제 대상이 이번 실행의 소유인지 확인하지 못한다. 기존 자료·이전 시험 결과를 지우거나 동시 실행과 충돌할 수 있다. UUID 이름으로 새 DB만 생성하고 자신이 만든 DB만 정리하는 방식, 또는 기존 DB가 있으면 거부하는 방식으로 수정하는 것이 좋다. 이번에는 새 서버의 미존재 DB임을 확인했으므로 기존 자료 손실은 없었다.

명시적 코드 스타일 위반 0건, 실행 안전성 판단사항 1건이다.

## Spec

기존 지적 3건은 해결됐다. `accounts.py:20–21,57`의 대문자 역할 매핑, `62–67`의 시간 공급, `81`의 이메일 정규화를 확인했다. 실제 DDL 테스트 3개와 D11의 ALTER 후 캐시 초기화(`test_auth_session.py:474,483`)도 확인했다. UI 바인딩과 로그인 시도 제한은 명시된 후속 범위이므로 누락 결함으로 계산하지 않는다. scrypt 동시 메모리·로그인 TX 내 실행은 기존에 수용한 위험으로 구분한다.

**1. 시험 fixture의 기존 자료 보호가 다르다.** 새 Railway fixture의 사전 DROP은 기존 `auth_test_engine()`의 “기존 테이블이 있는 DB에는 실행하지 않는다” 계약(`test_auth_session.py:45–46,57`)과 다르다. Standards 실행 안전성 항목과 같은 사항이다.

**2. 검증 상태 문구 갱신.** `hyundap/auth/docs/spec.md:28`의 “DB 통합 테스트는 격리 MySQL에서 아직 실행하지 않았다”와 PR 본문의 MySQL 미실행·coverage 미측정 문구는 이번 결과로 갱신할 수 있다. 당시 기록이므로 본체 기능 결함은 아니다.

현재 develop 기준 Spec 지적은 시험 보호 1건·검증 문서 1건이며, 새 고신뢰 운영 코드 결함은 발견하지 못했다.
