# 공통 라우팅 접근 방식 비교 시험

2026-10-28 `test-01`에서 별도 Railway 시험용 MySQL 8.4.13에 공통 스키마 1개와 회사 스키마 2개를 추가해 검증했다. 기존 회사 데이터와 스키마는 변경하지 않았다. 두 회사 계정에 시험 스키마 권한을 임시 부여하고 시험 후 회수했다. 시험 스키마와 합성 라우팅 행은 보존했다.

## 비교한 세 방식

1. **공통 테이블 직접 권한**: 두 회사 계정에 같은 라우팅 테이블의 SELECT·INSERT를 부여한다.
2. **회사별 제한 뷰**: 회사별 고정 조건과 `WITH CASCADED CHECK OPTION`이 있는 뷰에만 SELECT·INSERT를 부여한다. 뷰는 `SQL SECURITY DEFINER`로 시험했다.
3. **저장 프로시저**: 공통 테이블 직접 권한은 주지 않고 프로시저 실행만 허용한다. 프로시저는 시험용 계정-회사 매핑과 `USER()`를 비교해 조회·등록을 제한한다. 프로시저는 `SQL SECURITY DEFINER`로 시험했다.

## 해석과 한계

직접 테이블 권한은 공동 트랜잭션은 유지하지만 회사 행 격리를 보장하지 못했다. 뷰와 프로시저는 시험한 라우팅 조회·등록에서는 두 회사 모두 격리와 공동 롤백을 충족했다. 이 결과만으로 전체 애플리케이션을 안전하게 전환했다고 판단하지 않는다.

- 시험은 단순한 문서·라우팅 표본이며 실제 `companies`, `users`, `sessions`의 인증 검증과 `SELECT ... FOR UPDATE` 잠금 계약을 대체하지 않았다.
- 회사별 뷰는 회사 추가·권한 회수 시 뷰와 권한 관리가 필요하며, 뷰의 쓰기 가능성과 회사 조건 강제를 실제 스키마에서 다시 확인해야 한다.
- 프로시저의 계정-회사 매핑, `USER()` 식별 방식과 `SQL SECURITY DEFINER` 소유자 권한은 배포 환경에 맞게 검증해야 한다. 시험에서는 운영자 계정이 DEFINER였으며, 이를 운영 권한 설계의 권장안으로 확정하지 않는다.
- 두 방식 모두 회사 DB 계정 선택이 신뢰된 서버 인증 결과를 기반으로 이뤄져야 한다. 세션·역할·문서 상태 및 외부 작업 후 재검증을 대체하지 않는다.
- 브라우저 업로드·검색·실제 임베딩, 플랫폼 관리자 다회사 조회, 권한 변경·동시성·장애 복구는 검증하지 않았다.

다음 단계는 실제 v4 테이블과 인증 잠금 경계를 포함해 회사별 뷰 및 제한된 프로시저의 최소 권한을 각각 시험하고, 결과를 바탕으로 한 방법을 선택하는 것이다.
