# 실제 v4 인증·라우팅 접근 시험

2026-10-28 `test-01`에서 별도 Railway 시험용 MySQL 8.4.13에 실제 분리 v4 공통 DB 1개와 회사 DB 2개를 새로 생성했다. 기존 회사 DB와 업무 데이터는 변경하지 않았다. 두 회사 관리자와 각 회사의 제한 MySQL 계정을 사용했다.

## 시험 결과

| 항목 | 회사별 뷰 | 저장 프로시저 시험 어댑터 |
| --- | --- | --- |
| 실제 v4 문서·버전·작업·청크 및 공통 라우팅 생성 | 두 회사 성공 | 두 회사 성공 |
| 같은 연결에서 문서와 라우팅 공동 롤백 | 두 회사 성공 | 두 회사 성공 |
| 세션 행 잠금 유지 | 두 회사 성공 | 두 회사 성공 |
| 타사 DB 직접 조회·라우팅 회사 ID 위조 | 두 회사 거부 | 두 회사 거부 |
| 다른 회사의 세션으로 접근 | 두 회사 거부 | 두 회사 거부 |
| 폐기된 세션으로 접근 | 별도 시험하지 않음 | 두 회사 거부 |
| 공통 인증 원본 테이블 직접 조회 | 두 회사 거부 | 두 회사 거부 |

행 잠금은 문서 생성 트랜잭션이 열려 있을 때 별도 관리자 연결로 같은 세션을 갱신하려고 시도하고, MySQL 잠금 대기 시간 초과 1205를 확인했다. 롤백은 시험 문서와 라우팅 행이 모두 사라지는지 확인했다.

## 뷰 방식

회사별 공통 `companies`, `users`, `sessions`, `document_routes` 뷰를 만들고, 시험 과정에서 테이블 이름을 해당 뷰로 치환해 기존 `create_document_version`, `save_manifest`, `current_actor`를 호출했다. 다른 회사 DB와 인증 테이블 원본은 직접 조회할 수 없었고, 라우팅 뷰의 CHECK OPTION은 다른 회사 ID를 거부했다.

기존의 `SELECT ... FOR UPDATE`를 실행하려면 인증 관련 뷰에 `UPDATE(id)` 권한을 추가해야 했다. 이 권한으로 회사 사용자의 ID를 `id=id` 형태로 갱신하는 SQL이 실제로 허용됐다. 이는 변경 가능한 값을 실제로 변경해 보았다는 뜻은 아니지만, 잠금을 위한 권한이 SQL 갱신 권한도 함께 제공한다는 한계다. 뷰 DEFINER는 시험용 관리자 계정이다.

## 프로시저 방식

시험용 `SQL SECURITY DEFINER` 프로시저가 로그인 세션·사용자·회사 확인과 행 잠금을 수행하고, 다른 프로시저가 계정-회사 매핑을 확인한 후 라우팅을 등록·조회했다. 회사 계정에는 프로시저 EXECUTE와 자기 회사 DB DML만 주고 공통 인증·라우팅 테이블의 직접 권한은 주지 않았다.

기존 문서 생성의 공개 함수와 문서·버전·작업 삽입 및 청크 저장 함수는 사용했다. 다만 인증 검사, 라우팅 삽입과 버전 ID 라우팅은 시험 어댑터로 대체했다. 시험 어댑터는 기존 전체 기능의 완전한 구현이 아니며, 회사 관리자의 문서 생성 경로와 버전 ID 조회만 다룬다. 플랫폼 관리자, 오류 코드의 완전한 호환성과 다른 경로까지 지원한다는 결과가 아니다.

## 시험 후 상태와 미검증 범위

- 시험용 회사 계정에 추가한 v4 시험 DB 권한과 프로시저 EXECUTE 권한을 회수하고, 시험 로그인 세션을 폐기했다. 시험 DB·뷰·프로시저·합성 계정은 보존했다.
- 사용자 계정 비활성화·역할 변경·회사 비활성화 경쟁, 문서 게시·복구, 플랫폼 관리자 다회사 조회, 브라우저 업로드·검색·실제 임베딩과 보안 취약성 전반은 시험하지 않았다.
- 프로시저의 `USER()`와 계정-회사 매핑은 이 Railway SSH 터널·MySQL 계정 조합에서만 확인했다. 배포 연결 방식에서 신원 위조와 DEFINER 권한 범위를 별도 검토해야 한다.
- 실제 코드나 현재 앱의 DB 계정 연결을 변경하지 않았다. 테스트 전용 어댑터·로그는 `.git/p3-v4-*`에 있으며 저장소에 커밋하지 않는다.

다음 단계는 프로시저 방식의 신원·권한·동시성 경계를 구체화하고, 플랫폼 관리자와 기존 오류 계약을 포함한 격리 통합 테스트를 작성한 뒤 실제 적용 여부를 결정하는 것이다.
