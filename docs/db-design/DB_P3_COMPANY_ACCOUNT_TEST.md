# 회사별 MySQL 계정 트랜잭션 시험

2026-10-28, `test-01`에서 Railway의 별도 P3 시험용 MySQL 8.4.13으로 검증했다.
기존 Railway DB는 사용하지 않았다. 문서·라우팅 시험 데이터는 롤백했다.

## 검증 방법

- 이미 생성된 회사별 읽기 전용 시험 계정 중 하나에 업무·공통 DB의 시험 권한을 임시로 부여했다.
- 회사 엔진 선택만 시험 계정 연결로 대체하고 실제 `create_document_version`과 `save_manifest`를 호출했다. 공통 로그인은 기존 공통 앱 계정을 사용했다.
- 문서·버전·작업·청크와 공통 `document_routes`를 같은 연결에서 확인하고, 롤백 뒤 회사 문서와 공통 라우팅이 모두 사라지는지 확인했다.
- 회사 계정으로 다른 두 회사 DB를 직접 조회했을 때 모두 거부되는지 확인했다.

## 결과

| 시험 권한 | 결과 |
| --- | --- |
| 자기 회사 DB DML, 공통 `companies`·`users`·`sessions`·`document_routes` SELECT, `document_routes` INSERT | 기존 문서 생성이 `DB_UNAVAILABLE`로 실패. 세 공통 인증 테이블의 `SELECT ... FOR UPDATE`가 MySQL 오류 1142로 거부됨 |
| 위 권한에 공통 `companies`·`users`·`sessions` UPDATE 추가 | 문서·버전·작업·청크·라우팅 저장 및 회사 DB와 공통 DB의 공동 롤백 통과 |
| 위 권한으로 다른 회사 DB 직접 조회 | 다른 회사 2곳 모두 거부 |
| 공통 `users` 테이블 SELECT | 다른 회사 계정을 포함한 사용자 행 4개가 보임 |

이 결과는 회사별 계정으로 동일 서버의 DB 간 트랜잭션이 가능함을 보여 주지만, 현재 쿼리와 테이블 단위 권한을 그대로 적용하면 공통 인증 데이터 접근 범위를 회사별로 제한하지 못한다. 앱에서 안전한 회사 문맥 선택, 공통 정보 접근 경계와 세션·역할·문서 상태 검사는 별도로 필요하다.

## 시험 후 상태와 한계

임시로 추가한 공통 DB 권한과 자기 회사 DB 쓰기 권한을 회수했으며, 원래 회사 DB SELECT만 남겼다. 이 시험은 회사 계정 하나와 DB 저장 경로를 대상으로 했고, 회사별 계정을 실제 앱 연결에 적용하거나 브라우저 업로드·검색·벡터 저장을 검증하지 않았다. 시험용 계정과 세션은 Railway 시험 DB에 남아 있다.
