# DB 개선안 — 최종 v4 스키마·내부 저장 계약 단일화

작성일: 2026-10-27. 상태: 검토·후속 구현안. 현재 PR의 v3 호환 구조를 즉시 제거한 결과가 아니다.
목적은 Railway와 내부 코드가 동일한 최종 v4 계약만 사용하도록 해 호환 분기·중복 저장을 줄이는 것이다.
이번 문서 저장과 PR 피드백 조치는 실제 Railway DDL/DML 적용 승인을 의미하지 않는다.

## 현재 구조와 개선 방향

현재 v4는 v3 테이블을 보존하면서 버전·청크 테이블과 신규 컬럼을 추가한 혼합 구조다.
schema_migrations의 버전 숫자만 4로 변경해도 중복 컬럼이나 호환 코드가 사라지지는 않는다.
먼저 유지·통합·제거할 필드와 외부 인증 계약을 확정해야 한다.

| 영역 | 현재 | 개선안 |
|---|---|---|
| 신규 설치 | v3 재현 후 v4 확장 | 최종 11개 테이블·제약조건을 직접 생성하는 단일 진입점 |
| 업무 INSERT | 컬럼 존재 조회·동적 legacy.insert | 확정된 v4 컬럼에 바인딩하는 명시적 SQL |
| 작업 시도 횟수 | attempt_no와 attempts 동기화 | 단일 횟수 컬럼으로 확정하고 참조·제약·테스트 정리 |
| 작업 상태 저장 | P1 단계와 기존 종료/재시도 상태를 별도 갱신 | 결과 상태·처리 단계를 구분하되 한 저장 경로에서 원자 변경 |
| 문서 파일 정보 | documents와 document_versions에 이름·경로·해시 병존 | 버전별 파일 정보는 버전 테이블을 기준으로 통일. 업로더 등 업무 필드는 별도 보존 |
| 시간·세션 | 초/밀리초 선택과 기존/신규 만료 컬럼 | UTC Unix 초 기본·DATETIME UTC 정책 확정, 인증 담당과 만료 계약 통일 |

status와 stage는 결과 상태와 처리 단계로 의미가 다르다. 유휴 만료와 절대 만료도
서로 다른 정책이므로 컬럼 수를 줄이기 위해 의미를 합치거나 접근 검사를 삭제하지 않는다.
generation·content_revision·version_no도 동일 개념으로 가정하지 않고 실제 참조·동시성 역할을 확인한다.

## 제거·통합 후보

| 모듈·함수 | 최종 계약 확정 후 처리 |
|---|---|
| legacy.insert | 문서·작업 고정 INSERT로 대체하고 제거 검토 |
| legacy.finish_job, reset_job_for_retry | jobs_repo의 상태 저장 책임으로 모으고 보고서·상태 UPDATE 통합 검토 |
| legacy.epoch_now | 기존 시간 사용자와 인증 호출을 확인한 뒤 공통 시간 함수로 유지/이관. 합의 없이 삭제하지 않음 |
| 업무 경로의 get_table_columns 및 컬럼 존재 분기 | v4 고정 컬럼 직접 사용으로 교체. 관리용 snapshot/validate/audit는 유지 |
| prepare_sql, prepare_legacy_sql, key_definition 및 v3 지원 분기 | Railway 이행 완료 후 런타임에서 제거 검토. 필요 시 일회성 이행 산출물로 보존 |

현재 PR에서는 구조 확정 전 반복 조회 비용을 줄이기 위해 Engine별 컬럼 캐시를 적용한다.
이는 과도기 개선이며 v4 전용 코드의 동적 구조 조회를 영구 유지하자는 결정이 아니다.

## 진행 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 최종 물리 계약 | 전체 테이블·컬럼·키·상태·시간·인증 필드 유지/삭제 결정 | 단일 v4 DDL과 필드 매핑 문서 검토 가능 |
| 2 직접 생성 | 빈 DB 전용 생성 진입점 구현 | 기존 테이블이 있으면 거부. 순환 FK는 테이블 생성 후 연결. 최종 구조 검사·버전 4 기록 절차 검증 |
| 3 내부 단일화 | 고정 SQL·작업 상태·횟수 통합, 호환 분기 정리 | 기존 공개 함수의 입력·반환·오류·TX 계약 유지, 불필요한 클래스 래퍼 추가 없음 |
| 4 격리 검증 | 최종 생성 DB로 테스트 fixture 통일 | 권한·중복·원장·원자 저장·동시성·게시·복구·재시도 회귀 통과. 신규 생성과 승인된 최종 구조 일치 |
| 5 Railway 전환 | 실제 자료·인증/작업자 의존성 확인, 백업·복원·전환 절차 검토 | 별도 실제 적용 승인 후 수행. 데이터 보존/새 DB 전환 결정, 적용 후 구조·업무 검증 |

## 유지할 개발 기조와 효과 측정

일반 함수·dict와 기능별 모듈을 유지한다. 메인 함수는 업무 흐름, 보조 함수는
검사·조회·조립·저장 책임을 맡는다. 함수·모듈·클래스 유무를 DB 명세에 기록한다.
입력 검증·현재 권한·최종 중복 보호·포인터 CAS·실패 롤백은 축소 대상이 아니다.

기대 효과는 호환 함수·분기와 요청당 메타데이터 조회, 중복 상태 UPDATE 감소다.
신규 직접 생성 SQL도 추가되므로 전체 줄 수나 속도 개선 비율은 현재 확정하지 않는다.
변경 후 Python 함수/분기 수·SQL 호출 수·회귀 결과를 같은 기준으로 측정한다.
