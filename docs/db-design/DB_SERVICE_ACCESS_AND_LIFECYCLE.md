# 분리 DB 서비스 권한·원본 전송·프로세스 운영 계약

## 실행 범위

현재 지원 범위는 같은 MySQL 서버의 공통/회사 DB, 같은 호스트의 앱 프로세스,
공통 원본 저장 루트다. 여러 서버에서 각자 다른 로컬 파일을 쓰는 구성은 지원하지 않는다.
회사 잠금은 원본 루트의 `.locks`에서 OS 파일 잠금으로 조정한다. 모든 워커는 같은
설정/저장 경로를 사용한다. 기존 SQL 조건부 게시·권한 검증은 제거하지 않는다.
네트워크 파일시스템의 잠금 보장과 여러 서버의 임대/펜싱은 별도 설계 대상이다.

## 계정별 책임

| 계정 | 사용 시점 | 허용 범위 |
|---|---|---|
| 준비 관리자 DB_PROVISION_URL | 관리자 CLI/초기 설정 | DB·계정·프로시저 생성, GRANT, 등록부 creating/ready/failed 변경 |
| 공통 서비스 DATABASE_URL | 로그인·세션 검증·라우팅 조회 | companies/users/company_databases/document_routes/schema_migrations SELECT, sessions SELECT/INSERT/UPDATE |
| 회사별 계정 | 해당 회사 문서 업무 | 자기 회사 업무 4개 표 DML, 소속·버전 표 SELECT, 회사 정보 VIEW와 지정 프로시저 실행 |

전체 관리자라는 앱 역할은 MySQL root 권한을 의미하지 않는다. 전체 관리자도
서버에서 권한을 확인한 뒤 대상 회사 계정으로 문서 업무를 수행한다.

`db.access_policy.grant_control_service_access(admin_engine, username, host)`는
관리자가 미리 만든 **권한 없는 신규 공통 서비스 계정**에 위 권한을 부여한다.
기존 계정의 넓은 권한을 자동 회수하지 않으므로 root에 실행해 최소 권한이 됐다고
간주하면 안 된다. oauth_states/audit_logs/login_attempts는 행 SELECT를 주지 않고
REFERENCES만 부여하여 기존 information_schema 기반 구조 검증에서 표가 보이게 한다.
이 권한만으로 DDL이나 행 조회를 수행할 수 없음을 격리 MySQL에서 검증한다.

회사 계정에는 공통 표 직접 조회 권한을 주지 않는다. 기존 DEFINER 프로시저는 호출
계정과 고정 회사 ID를 확인한다. 문서 저장과 공통 라우팅 등록은 같은 회사 연결의
트랜잭션으로 실행되므로 같이 커밋/롤백된다. 권한 분리를 이유로 연결을 둘로 나누지 않는다.

## 적용 순서

1. 격리 MySQL에서 서비스 계정의 정상 업무와 금지 작업을 확인한다.
2. 준비 관리자가 신규 계정을 만들고 명시적 권한표를 적용한다. 비밀번호는 채팅·로그에 남기지 않는다.
3. DATABASE_URL은 서비스 계정, DB_PROVISION_URL은 관리자 전용 환경에 설정한다.
4. 회사별 계정을 모두 준비한 뒤 HYUNDAP_DB_COMPANY_ACCOUNTS=1로 연결한다.
5. 로그인·세션 폐기·회사 생성·문서 업무·공동 롤백 검증 후 운영 전환한다.

이번 개선은 실제 Railway GRANT·계정·스키마 변경을 실행하지 않는다. 운영 적용은 별도 작업이다.

## 비밀 파일

현재 선택한 `HYUNDAP_COMPANY_CREDENTIALS_SOURCE=file`을 유지한다. JSON은 평문이므로
앱/준비 관리자 OS 계정만 읽고 쓸 수 있게 파일과 상위 디렉터리 접근 권한을 제한한다.
Git 제외를 유지하며 읽기/쓰기/교체는 같은 파일 잠금을 사용한다. 환경변수 모드를 선택하면
누락 시 로컬 파일로 대체하지 않는다. 회사별 비밀이 없으면 root로 대체하지 않는다.

`save_credential`은 비밀번호 교체 API가 아니다. 같은 값은 멱등, 다른 값은 CONFLICT다.
계정 교체는 요청을 중지하고 관리자가 DB와 비밀을 맞춘 뒤 모든 워커의 해당 엔진을
무효화하거나 재시작하는 절차다. 준비 실패 시 회사와 미완료 계정을 잠금/비활성으로 유지한다.

## 원문 다운로드

DB의 `prepare_original_download`는 활성 원본만 검증한 임시 사본으로 반환한다.
호출자가 temporary.cleanup을 소유한다. UI는 원본 경로를 Gradio 캐시에 공개하지 않고,
HttpOnly/SameSite 쿠키에 묶인 60초·1회 링크를 제공한다. 실제 전송 시 세션·회사·버전·
파일 해시를 다시 검사하고 완료/실패 후 사본을 정리한다. 전송 시작 후 도착한 권한 변경은
이미 전송된 바이트를 회수할 수 없다. 다운로드 티켓에는 세션 토큰을 넣지 않는다.

티켓은 프로세스 메모리에 저장되므로 다중 워커에서는 세션 고정이 필요하다. 다른 워커나
앱 재시작 후 링크는 거부된다. 사용자 정의 Gradio launch는 DownloadMiddleware를 설치해야
하며 기본 `python -m hyundap.app`은 이를 연결한다. 과거 버전 다운로드는 별도 계약이다.

## 연결 풀 수명

`tenancy.get_company_engine`은 활성 상태를 매번 확인하고 최대 32개 엔진을 재사용한다.
`invalidate_company_engine(company_id)`는 해당 회사 엔진만 캐시에서 제거한다.
이미 사용 중인 연결은 종료까지 유지되므로 즉시 권한 회수 기능으로 사용하지 않는다.
회사 비활성화는 서버 권한 재검증으로 신규 업무를 거부하며 풀 정리는 별도 수행한다.
작업 잠금 사전은 선택적 무효화에서 삭제하지 않는다.

`db.lifecycle.service_lifespan`은 기본 Gradio 서버 종료 시 회사 풀과 이미 생성된 공통 풀을
정리한다. 사용하지 않은 DB에 종료 목적으로 새 연결을 만들지 않는다. 강제 kill은 이 훅을
실행하지 못하므로 OS/DB의 연결 종료에 의존한다. 캐시 생성·상한·무효화 개수만 로깅하고
접속 URL·비밀번호는 기록하지 않는다. 실제 대규모 회사 수의 지연·CPU·메모리 용량 판정은
별도 성능 시험이며 32개 경계 단위 테스트와 혼동하지 않는다.
