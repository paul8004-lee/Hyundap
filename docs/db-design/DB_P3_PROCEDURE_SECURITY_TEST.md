# 회사별 DB 프로시저 보안·계약 시험

2026-10-28 `test-01`에서 기존 Railway P3 시험용 MySQL 8.4.13의 별도 v4 시험 DB를 사용했다. 시험용 회사 계정 두 개에 필요한 권한을 잠시 부여했으며 시험 후 회수했다. 시험 세션은 폐기했고 플랫폼 관리자 시험 계정과 시험 스키마는 보존했다. 실제 앱 코드와 기존 회사 데이터는 수정하지 않았다.

## 검증 결과

| 항목 | 결과 |
| --- | --- |
| 회사 계정 본인 세션과 자기 회사 | 두 회사 통과 |
| 다른 회사 ID 또는 다른 회사 세션 | 두 회사 모두 `ACCESS_DENIED` |
| 위조 토큰 | 두 회사 모두 `SESSION_EXPIRED` |
| 공통 users·sessions·companies·document_routes·계정 매핑 직접 조회 | 두 회사 모두 거부 |
| 세션·사용자·회사 잠금 | 별도 연결의 각 갱신이 MySQL 오류 1205로 대기 후 거부됨 |
| 관리자 역할을 직원으로 변경 | `ACCESS_DENIED` |
| 사용자 비활성화 또는 세션 폐기 | `SESSION_EXPIRED` |
| 회사 비활성화 | `ACCESS_DENIED` |
| 플랫폼 관리자 | 기존 앱은 두 회사 모두 허용하지만 시험 프로시저는 모두 `ACCESS_DENIED` |
| 존재하지 않는 문서·버전·작업의 라우팅 등록 | 시험 프로시저가 허용함. 해당 시험 트랜잭션은 롤백 |

사용자 역할·활성 상태와 회사 활성 상태는 별도 v4 시험 DB에서 변경해 검증한 뒤 원래 값으로 복구했다. 잠금 시험은 인증 프로시저가 열린 트랜잭션에서 반환한 뒤 각 행의 변경을 별도 연결로 시도했다.

## 적용 전 해결해야 하는 문제

1. **플랫폼 관리자**: 현재 프로시저는 `company_admin`만 허용하므로 기존 전체 관리자의 회사 접근 계약과 호환되지 않는다. 플랫폼 관리자도 서버가 신뢰하는 회사별 DB 계정을 선택할 수 있게 하되, 사용자에게 다른 회사 계정이나 URL 선택 권한을 주지 않아야 한다.
2. **라우팅 정합성**: 시험용 라우팅 등록 프로시저는 호출 계정의 회사 ID만 확인한다. 해당 회사 DB에 문서·버전·작업이 실제로 존재하고 서로 일치하는지 확인하지 않아 임의 식별자를 등록할 수 있다. 보완 시 현재의 단일 트랜잭션·롤백과 중복·실패 계약도 검증해야 한다.
3. **인증 및 오류 계약**: 여기서 확인한 오류는 테스트한 사례에 대한 MySQL SQLSTATE 45000 메시지와 앱 오류의 비교다. 플랫폼 역할, 인증 버전 변경, 모든 만료 조건, 식별자 오류, DB 장애와 기존 오류 우선순위를 전부 검증한 것은 아니다. SQL 오류를 애플리케이션 예외로 안전하게 변환하는 실제 어댑터도 필요하다.
4. **신원·DEFINER 경계**: `USER()`와 MySQL 계정 매핑은 이번 SSH 터널을 통한 두 계정에서만 확인했다. 프록시나 다른 연결 환경에서의 신원 보장, 계정 생성·회수, 프로시저 DEFINER의 최소 권한을 추가 검토해야 한다.

이 결과는 시험 프로시저를 그대로 적용하기에 부족함을 보여 준다. 원본 문서 게시·복구, 검색·답변 전후 재검증, 실제 업로드·임베딩과 플랫폼 관리자의 종단 간 경로는 시험하지 않았다. 기존 문서 권한 검증은 제거하지 않았다.
