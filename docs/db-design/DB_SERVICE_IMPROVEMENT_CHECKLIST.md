## 항목 1 진행

## 항목 3 완료

`tenancy.processing_lock`의 분리 DB 모드에 OS 파일 잠금을 연결했다.
같은 호스트·공통 원본 저장 루트의 프로세스끼리 서버/공통 DB/회사/작업 종류를 구분해
직렬화한다. 기존 RLock만으로 보호하던 구간이며 외부 API 동안 SQL TX를 유지하지 않는다.
잠금 대기는 최대 30초, 실패는 DB_UNAVAILABLE다. 다중 서버·네트워크 파일시스템은
이 계약에 포함하지 않으며 별도 분산 작업 소유권 설계가 필요하다.

검증: 격리 split suite 22개 통과(68.803초), 추가 프로세스 종료·재시도 경쟁 1개 통과
(3.883초). 서로 다른 실제 Python 프로세스에서 같은 회사 동일 파일은 성공1·중복거부1,
다른 회사는 수집 barrier에 함께 도달해 모두 성공했다. 임베딩 직전 exit23 후 기존 활성
버전·원본을 보존하고 두 재시도 프로세스 중 한 번만 게시, 버전 총 2개를 유지했다.
AI·벡터는 대역, SQL은 격리 MySQL이다. 여러 서버 안전성을 주장하지 않는다.

## 항목 4 완료

`access_policy.py`에 신규 공통 서비스 계정용 권한표·관리자 적용 함수를 추가했다.
일반 서비스는 인증·세션·등록 조회만 가능하고 회사 DB는 전용 계정으로 연결한다.
`company_admin.admin_transaction`으로 등록부 변경도 준비 관리자 연결로 이동했다.
최소 권한 서비스에 회사 등록부 쓰기 권한을 추가하지 않는다.

최소 권한 시험에서 실제 로그인·신규 회사 등록·회사 원본 업로드·다운로드·로그아웃 성공,
공통 미사용 민감 표 조회·DDL·세션 DELETE·등록부 UPDATE·회사 직접 조회 거부를 확인했다.
회사 계정의 라우팅 프로시저 호출 뒤 장애를 주입해 문서/버전/공통 라우팅 공동 롤백도 확인했다.
첫 split suite 24개 중 기존 공통 계정 모드 1개 실패: 등록부 쓰기 연결 변경으로
CURRENT_USER가 관리자를 가리켰다. 실제 업무 연결에서 계정을 읽도록 수정했다.
수정 후 해당 기존 모드·최소 권한·등록 실패 잠금 3개 재검증 통과(8.084초).
권한표와 비밀 교체·다중 워커 제약은 DB_SERVICE_ACCESS_AND_LIFECYCLE.md에 기록했다.
실제 Railway 계정·권한은 변경하지 않았다.
